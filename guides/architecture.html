Thème

PR Dashboard

Tauri 2 React 19 TypeScript Rust GitHub Enterprise GitLab

Application desktop qui affiche en temps réel les Pull Requests et Merge Requests ouvertes sur plusieurs repositories GitHub Enterprise et GitLab. Elle tourne dans le system tray, envoie des notifications desktop, et ne nécessite aucun navigateur.

Comment ça marche en une phrase

Le frontend React interroge le backend Rust via des commandes Tauri. Le Rust fait les appels HTTP vers l'API GraphQL de GitHub ou de GitLab selon la source du repo, et renvoie les PRs/MRs dans un modèle commun. React Query gère le cache et le re-polling automatique.

Flux de données principal

Voici comment les données circulent du stockage jusqu'à l'affichage, et comment les événements PR déclenchent les notifications.

React Query gère automatiquement le cache et le re-fetch. Chaque repository a sa propre query (clé ["prs", provider, owner, name]), ce qui permet des rafraîchissements indépendants et un affichage partiel si un repo est lent. Le provider fait partie de la clé pour que deux repos homonymes hébergés sur des sources différentes ne partagent pas de cache.

APIs GitHub / GitLab

L'application supporte GitHub Enterprise Server (GHES) et GitLab (self-hosted ou gitlab.com). L'URL de base de chaque source est configurable ; tous les endpoints en sont dérivés automatiquement.

UsageGitHubGitLab
Liste des PR/MR{githubUrl}/api/graphql{gitlabUrl}/api/graphql
Vérification de merge{githubUrl}/api/v3/repos/{owner}/{repo}/pulls/{number}{gitlabUrl}/api/graphql
Web{githubUrl}/{owner}/{repo}/pulls{gitlabUrl}/{namespace}/{repo}/-/merge_requests

Authentification : Authorization: Bearer <token> dans les deux cas. Scopes requis : repo (GitHub), read_api (GitLab). commands/fetch_prs.rs ne fait que router vers providers::github ou providers::gitlab selon le provider du repo.

GraphQL GitHub — fetch_repo_prs

Un seul appel par repository pour récupérer les 50 PRs ouvertes les plus récentes :

sequenceDiagram participant R as 🦀 Rust participant G as GitHub GraphQL R->>G: POST /api/graphql
Authorization: Bearer token Note over R,G: query GetOpenPRs($owner, $repo, first: 50) G-->>R: pullRequests nodes[]
(number, title, url, isDraft,
reviewDecision, author, labels, reviews) R->>R: map nodes → PullRequest[]
extraire approvers depuis reviews R-->>R: RepoPRs { repo, prs, lastUpdated }

Note GHES : Le champ requestedReviewers n'est pas disponible sur toutes les versions de GitHub Enterprise Server — il a été retiré de la query pour éviter une erreur GraphQL bloquante.

REST GitHub — check_pr_merged

Appelé uniquement quand une PR disparaît de la liste ouverte, pour distinguer une fermeture d'un merge :

GET {githubUrl}/api/v3/repos/{owner}/{repo}/pulls/{number}
→ { state: "closed", merged_at: "2024-..." }
  merged si merged_at ≠ null

GraphQL GitLab — fetch_repo_prs

Le chemin projet est {owner}/{name}, le owner d'un repo GitLab contenant le namespace complet (sinequa/rnd).

query GetOpenMRs($fullPath: ID!, $first: Int!) {
  project(fullPath: $fullPath) {
    mergeRequests(state: opened, sort: UPDATED_DESC, first: $first) {
      nodes {
        iid title webUrl draft createdAt updatedAt
        sourceBranch targetBranch approved
        author { username avatarUrl }
        labels(first: 10) { nodes { title color } }
        approvedBy(first: 20) { nodes { username avatarUrl } }
        reviewers(first: 20) {
          nodes { username avatarUrl mergeRequestInteraction { reviewState } }
        }
      }
    }
  }
}

Particularités du schéma : state: opened est en minuscules alors que sort: UPDATED_DESC est en majuscules ; toutes les sous-connexions sont bornées par first: pour rester sous le plafond de complexité (250 en authentifié).

ChampSource GitLabTraitement
numberiidiid est une String → parsée en u64, MR ignorée si le parse échoue
labels[].colorcolorGitLab renvoie #RRGGBB, GitHub RRGGBB → normalize_hex()
approversapprovedBy.nodes—
avatarUrlavatarUrlabsolutize() : peut être relative ou protocol-relative
reviewDecisiondérivéREQUESTED_CHANGES → CHANGES_REQUESTED, sinon approved → APPROVED, sinon REVIEW_REQUIRED

Sémantique de approved : « toutes les approbations requises sont obtenues ». Une MR approuvée 1 fois sur 2 reste REVIEW_REQUIRED tout en exposant ses approvers → fond « partiellement approuvée », comme sur GitHub. Ne pas dériver APPROVED d'un approvedBy non vide.

GraphQL GitLab — check_pr_merged

GraphQL plutôt que REST v4 : même endpoint, même auth, et aucun percent-encoding du chemin projet à gérer.

query MrState($fullPath: ID!, $iid: String!) {
  project(fullPath: $fullPath) { mergeRequest(iid: $iid) { state } }
}
→ merged si state == "merged"

Types de données

interface PullRequest {
  number:             number;
  title:              string;
  url:                string;
  isDraft:            boolean;
  createdAt:          string;          // ISO 8601
  updatedAt:          string;
  headRefName:        string;          // branche source
  baseRefName:        string;          // branche cible
  reviewDecision:     ReviewDecision;
  author:             Reviewer;
  labels:             Label[];
  requestedReviewers: Reviewer[];      // toujours vide (non supporté GHES)
  approvers:          Reviewer[];      // extrait des reviews state === "APPROVED"
}

type ReviewDecision = "APPROVED" | "CHANGES_REQUESTED" | "REVIEW_REQUIRED" | null;

interface Reviewer {
  login:     string;
  avatarUrl: string;
}

interface RepoPRs {
  repo:        string;       // "owner/name"
  prs:         PullRequest[];
  error:       string | null;
  lastUpdated: string | null;  // horodatage UTC du dernier fetch
}

type Provider = "github" | "gitlab";

interface Config {
  githubToken:     string;
  githubUrl:       string;   // défaut: https://github.sinequa.com
  gitlabToken:     string;
  gitlabUrl:       string;   // défaut: https://gitlab.chapsvision.in
  refreshInterval: number;   // secondes, défaut: 60
  repositories:    RepositoryConfig[];
}

interface RepositoryConfig {
  id:       string;
  provider: Provider;  // défaut: "github"
  owner:    string;    // GitHub : le owner · GitLab : le namespace complet ("sinequa/rnd")
  name:     string;
  label?:   string;
}

interface PREvent {
  type:     "new_pr" | "merged";
  provider: Provider;  // pilote la terminologie : "New PR" ou "New MR"
  repo:     string;    // "owner/name" — affiché tel quel
  prNumber: number;
  prTitle:  string;
  url:      string;
}

Le modèle est commun aux deux sources : une Merge Request GitLab est mappée sur PullRequest côté Rust, si bien qu'aucun composant d'affichage n'a besoin de connaître la source. Seuls la terminologie et les liens en dépendent, via prTerm(), prPrefix() et repoWebUrl().

Chargement initial — squelettes

Au premier lancement, avant que les données GitHub soient disponibles, RepoGroup affiche 3 cartes squelettes animées (animate-pulse) qui reproduisent la structure de PRCard.

Condition : isLoading && prs.length === 0 — les squelettes n'apparaissent qu'au premier fetch. Les refreshs en arrière-plan restent discrets : seul le spinner dans l'en-tête du groupe tourne.

Système de notifications

Détection des changements de PR

La détection repose sur un useRef qui conserve l'état précédent des PRs entre les renders :

Premier démarrage : le useRef est vide, donc aucune notification ne tire lors du premier fetch. Les notifications démarrent à partir du second poll.

Toasts in-app

Chaque ToastItem : slide-in depuis la droite, barre de progression 5s, cliquable pour ouvrir la PR, bouton ✕ manuel.

Enregistrement AUMID Windows

Sur Windows, les Toast Notifications requièrent un enregistrement dans le registre :

HKCU\SOFTWARE\Classes\AppUserModelId\com.sinequa.prdashboard
  DisplayName = "PR Dashboard"

Cet enregistrement est idempotent et ne nécessite pas de droits admin (HKCU). Sans cette clé, tauri-plugin-notification échoue silencieusement et l'app n'apparaît pas dans Paramètres → Notifications.

Frontend ↔ Backend (IPC)

Tauri expose un système de RPC via invoke() côté frontend. Les handlers Rust sont enregistrés dans lib.rs via tauri::generate_handler!.

get_config—Lit la config depuis le store JSON
save_configconfigPersiste la config sur disque
fetch_repo_prsprovider, owner, repo, token, baseUrlGraphQL GitHub ou GitLab → RepoPRs
check_pr_mergedprovider, owner, repo, number, token, baseUrlREST v3 (GitHub) ou GraphQL (GitLab) → bool

// Côté frontend (TypeScript)
import { invoke } from "@tauri-apps/api/core";

// token et baseUrl sont résolus par repo via providerCreds(config, repo)
const { token, baseUrl } = providerCreds(config, repo);
const data = await invoke("fetch_repo_prs", {
  provider: "gitlab",
  owner: "sinequa/rnd",
  repo:  "mon-repo",
  token,
  baseUrl,
});
// → RepoPRs

async fn fetch_repo_prs(provider: Option<Provider>, owner: String, repo: String,

  -> Result<RepoPRs, String> { … }   // dispatch vers providers::github | providers::gitlab

Lancer l'application

Prérequis

Node.js, Rust toolchain, WebView2 (Windows — déjà présent sur Windows 11).

# Développement — hot-reload frontend, rebuild Rust si modifié
npm run tauri dev
# Build de production
npm run tauri build
